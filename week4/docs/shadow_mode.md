# Shadow mode: เทียบ runner ของเรากับ g1_ctrl (งาน 4.4–4.5)

## แนวคิด
ให้ **g1_ctrl คุมหุ่นใน sim** ตามปกติ ส่วนโปรแกรมเรา**ฟังอย่างเดียว**:
```
                 ┌──────── rt/lowstate ────────┐
unitree_mujoco ──┤                             ├──▶ runner ของเรา: obs → ONNX → q_des(เรา)
     ▲           └──▶ g1_ctrl (Velocity) ──────┘          │
     └──────────────── rt/lowcmd ◀─────┬───────────────────┤ (subscribe ฟัง)
                                       └──▶ q_des(g1_ctrl) │
                                                           ▼
                                                เทียบ q_des(เรา) − q_des(g1_ctrl)  → CSV
```
ถ้าตัวเลขตรงกัน แปลว่าเราเข้าใจ observation และ action ถูกทุกตัว ถ้าไม่ตรง ตัวเลขจะบอกว่าข้อต่อไหน/term ไหนผิด
**ปลอดภัย:** เรา subscribe อย่างเดียว ไม่มี publisher ในโปรแกรม จึงไม่แย่ง g1_ctrl

## ขั้นตอน
1. `~/g1_study/start_sim.sh`
2. รัน g1_ctrl (ตัวจริงจาก repo ก็ได้ เพราะเราไม่แก้มัน หรือสำเนาจากสัปดาห์ 3) **ไม่ใส่ `--network`** = sim
3. ตามที่ g1_ctrl แนะนำ: Pause MuJoCo → Load key 0 (stand_ready) → กด `u` (FixStand) → `v` (Velocity) → Run MuJoCo (เท้าแตะพื้น ไม่ต้องห้อย)
4. **ไม่กดปุ่มเดิน** (cmd = 0) รอให้ผ่าน soft start 0.5 s
5. รัน runner ของเรา (domain 1, `lo`) เก็บ 10–20 วินาทีลง CSV
6. (4.5) ระหว่างเก็บ ลองลากลำตัวใน MuJoCo ให้ก้ม/เอียงเล็กน้อย ไม่เกิน 0.85 rad ไม่งั้นจะเข้า Passive

## สิ่งที่ runner ต้องมี (โครง ไม่ใช่เฉลย)
- subscriber `rt/lowstate` (สัปดาห์ 1) เก็บ msg ล่าสุดใน lock
- subscriber `rt/lowcmd` (สัปดาห์ 2) เก็บ `motor_cmd[slot].q` ล่าสุดใน lock
- loop 50 Hz: build_obs → ONNX → q_des(เรา) → อ่าน q_des(g1_ctrl) ของ 23 slot → บันทึกลง CSV
- เก็บ raw action ของเราไว้ใช้เป็น `last_action` ใน step ถัดไป

## ทำไมค่าอาจไม่ตรงเป๊ะ (และอะไรคือ "ปกติ")
| สาเหตุ | ผล | แก้/ยอมรับ |
|---|---|---|
| **อ่าน lowstate คนละจังหวะ** g1_ctrl กับเราเรียก policy ไม่พร้อมกัน (ห่างกันได้ถึง 20 ms) | ต่างกันเล็กน้อยตลอด โดยเฉพาะตอนเคลื่อนไหว | ปกติ เทียบตอนยืนนิ่ง |
| **`last_action` คนละชุด** ของเราเริ่มจาก 0 ตอนเราเปิดโปรแกรม ของ g1_ctrl เริ่มตอนกด `v` | ช่วงแรกต่าง แล้วค่อยๆ เข้าหากัน (policy นิ่ง → action นิ่ง) | ตัดช่วง 1–2 s แรกทิ้ง |
| **gait_phase** ถ้า g1_ctrl เคยเดินมาก่อน phase จะไม่ตรง | ตอนเดินจะต่างมาก | ใช้ cmd = 0 (phase = (0,0) ทั้งคู่) |
| **cmd** sim ใช้คีย์บอร์ดใน g1_ctrl เราอ่านไม่ได้ | ถ้ากดเดิน เราจะไม่รู้ | ไม่กดเดิน |
| **soft start** 0.5 s แรก lowcmd ≠ q_des | ต่างมากช่วงแรก | ตัดทิ้ง |
| **float32 vs float64** | ต่างกันระดับ 1e-6 | ไม่สนใจ |

ถ้าเกิน 0.01 rad ตอนนิ่ง ให้สงสัยตามลำดับนี้: ลำดับข้อต่อ → ลบ default → gravity → `last_action` raw/processed → ลำดับ term ใน obs

## วิเคราะห์ CSV
- คอลัมน์ที่แนะนำ: `t, q_des_ours[23], q_des_g1[23], obs[80]`
- พล็อต `q_des_ours − q_des_g1` ของทุกข้อต่อเทียบกับเวลา
- หา max/mean ของ |error| แยกตามข้อต่อ แล้วดูว่าข้อต่อไหนแย่สุด แล้วใช้ map กลับไปหา term ที่น่าจะผิด

## คำถามเช็ค
1. ทำไม shadow mode ถึงปลอดภัยกว่าให้ Python คุมหุ่นเองตั้งแต่แรก
2. ถ้า error ของทุกข้อต่อเป็น 0 พอดี (ทุก step) แปลว่าอะไร น่าสงสัยไหม
3. error ตอนหุ่นนิ่งเล็ก แต่ตอนลากหุ่นใหญ่ขึ้น บอกอะไรเรา
